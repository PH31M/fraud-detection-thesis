# fraud-detection-thesis

Fraud detection thesis project using the PaySim mobile money transaction dataset.

Dataset source: [PaySim1 on Kaggle](https://www.kaggle.com/datasets/ntnu-testimon/paysim1)

## Dataset Setup

The raw PaySim dataset is not committed to Git because it is large. To reproduce the project, download it from Kaggle:

[https://www.kaggle.com/datasets/ntnu-testimon/paysim1](https://www.kaggle.com/datasets/ntnu-testimon/paysim1)

After downloading and extracting the dataset, place the CSV file in the `data/` folder and rename it to:

```text
data/paysim.csv
```

The downloaded Kaggle file is commonly named similar to:

```text
PS_20174392719_1491204439457_log.csv
```

Rename it to `paysim.csv` so the notebooks can read it without code changes.

Expected local `data/` folder before running notebooks:

```text
data/
├── paysim.csv
└── .gitkeep
```

Generated files such as `data/engineered_features.pkl` and `data/processed_split.pkl` will be created automatically by the notebooks. They are ignored by Git and should not be committed.

## Environment Setup

Create and activate a Python virtual environment, then install dependencies. This installs everything needed to run `notebooks/01`–`06`.

### Windows PowerShell

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -r requirements.txt
```

### macOS / Linux

```bash
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

`requirements.txt` is a pinned snapshot of the environment the notebooks were
last run in (Python 3.14). It does not include `fastapi`/`uvicorn`/`pydantic`/
`pytest` — those belong to the separate `fraud-service/` app and are pinned
in [`fraud-service/requirements.txt`](fraud-service/requirements.txt) instead;
install that separately if you want to run the service (see below).

## Notebook Run Order

Run the notebooks in this exact order:

1. `notebooks/01_eda.ipynb`
2. `notebooks/02_feature_engineering.ipynb`
3. `notebooks/03_prepare_dataset.ipynb`
4. `notebooks/04_baseline_models.ipynb`
5. `notebooks/05_extension_smote_xgboost.ipynb`
6. `notebooks/06_shap_cost_sensitive.ipynb`

This order matters because later notebooks depend on artifacts generated by earlier notebooks.

### About the `v2_64_16_20_val_split` suffix

Most filenames under `results/` carry the suffix `v2_64_16_20_val_split`.
`v2` marks this as the second split/versioning scheme used in the project —
an earlier iteration used a plain 80:20 train:test split with no separate
validation set (its artifacts were kept for a while under a
`_deprecated_80_20` suffix and have since been removed; the split policy
below is the only one still in use). `64_16_20_val_split` spells out the
current policy: a stratified 64% train / 16% validation / 20% test split,
with the validation split used to select the classification threshold before
it is ever applied to the locked test set. `data/processed_split.pkl` and
`results/split_summary_v2_64_16_20.csv` (written by notebook 03) are the
source of truth for this split; every downstream notebook checks its
`split_version` metadata against `v2_64_16_20` and raises an error if it
doesn't match, so the suffix on a results file also tells you which split
produced it.

## Pipeline Details

### 1. Exploratory Data Analysis

`notebooks/01_eda.ipynb` reads:

```text

```

It checks:

- dataset shape and column types
- missing values and duplicate rows
- descriptive statistics
- class imbalance between normal and fraud transactions
- fraud distribution by transaction type
- transaction amount distribution
- balance-related anomalies


### 2. Feature Engineering

`notebooks/02_feature_engineering.ipynb` reads:

```text
data/paysim.csv
```

It creates fraud-related features:

- `errorBalanceOrig = newbalanceOrig + amount - oldbalanceOrg`
- `errorBalanceDest = oldbalanceDest + amount - newbalanceDest`
- `balance_change_orig` / `balance_change_dest`: relative change in the
  origin/destination balance, with the old balance replaced by `1` when it
  is `0` to avoid dividing by zero
- one-hot encoded transaction type columns (`type_CASH_IN`, `type_CASH_OUT`,
  `type_DEBIT`, `type_PAYMENT`, `type_TRANSFER`)

It removes raw identifier columns that are not used for modeling:

- `nameOrig`
- `nameDest`

It writes:

```text
data/engineered_features.pkl
```

### 3. Dataset Preparation

`notebooks/03_prepare_dataset.ipynb` reads:

```text
data/engineered_features.pkl
```

It prepares the modeling dataset by:

- separating features `X` and target `y`
- using `isFraud` as the target label
- dropping `isFlaggedFraud`
- performing a stratified 64:16:20 train/validation/test split (`random_state=42`)
- keeping the test set locked for final reporting
- fitting a `StandardScaler` on the training set and storing both the
  unscaled and scaled versions of each split

It writes:

```text
data/processed_split.pkl
results/split_summary_v2_64_16_20.csv
```

**Note on scaling:** the scaler stored in `data/processed_split.pkl` is only
used for the Logistic Regression / KNN baselines in notebook 04. The
XGBoost models trained in notebook 05 (and the SHAP explainer built on them
in notebook 06) are trained directly on the *unscaled* feature DataFrame —
tree-based models don't need feature scaling, and `fraud-service/` reproduces
this exactly (see `fraud-service/README.md`).

### 6. SHAP and Cost-Sensitive Evaluation

`notebooks/06_shap_cost_sensitive.ipynb` loads `xgb_smote_model_v2_64_16_20_val_split.pkl`
and performs:

- SHAP summary/force plot generation (`shap.TreeExplainer` on the unscaled model)
- cost-sensitive threshold selection: a sweep over thresholds on the
  **validation** split, minimizing cost = `FP × 1 + FN × 50`, then applying
  the selected threshold to the **test** split exactly once

The threshold-selection workflow is:

```text
train models -> sweep thresholds on validation -> lock threshold -> report once on test
```

It writes:

```text
results/shap_feature_ranking_v2_64_16_20_val_split.csv
results/shap_summary_plot_v2_64_16_20_val_split.png
results/shap_force_plot_TP_v2_64_16_20_val_split.png
results/shap_force_plot_FN_v2_64_16_20_val_split.png
results/cost_sensitive_validation_sweep_v2_64_16_20_val_split.csv
results/cost_sensitive_selected_thresholds_v2_64_16_20_val_split.csv
results/cost_sensitive_test_final_v2_64_16_20_val_split.csv
results/cost_sensitive_provenance_v2_64_16_20_val_split.json
```

The selected threshold for `XGBoost + SMOTE` is **0.95**; the confirmed
test-set result at that threshold (`cost_sensitive_test_final_v2_64_16_20_val_split.csv`)
is `tn=1,270,877 fp=4 fn=4 tp=1,639`, i.e. precision = recall = f1 ≈ **0.9976**.
This is the model and threshold `fraud-service/` serves.

4. Rename the raw CSV to `paysim.csv`.
5. Put it under `data/paysim.csv`.
6. Create a virtual environment.

8. Run notebooks `01` to `06` in order.
9. Check generated figures in `reports/figures/`.
10. Check generated model outputs and evaluation tables in `results/`.

## Fraud Detection Service

[`fraud-service/`](fraud-service/) is a FastAPI service that packages the
trained `XGBoost + SMOTE` model (`results/xgb_smote_model_v2_64_16_20_val_split.pkl`)
behind a `/predict` API, plus a small built-in HTML test page. It reproduces
the exact feature engineering and (lack of) scaling from notebooks 02/05/06,
and is tested with a 24-case pytest suite. See
[`fraud-service/README.md`](fraud-service/README.md) for how to run it,
its API shape, and manual test results. It is a separate, self-contained
sub-project — it has its own `requirements.txt` and does not affect the
notebook pipeline above.
